这是 Claude Code 系列的第七篇，也是整个系列最硬核的一篇。

前几篇我们把 Claude Code 的「能力」拉满了——CLAUDE.md 让它了解你的项目，settings 控制它的行为，Skills 封装工作流，MCP 连接外部世界，Hooks 把确定性逻辑交给外部系统。如果你一路跟下来，你的 Claude Code 已经比 90% 的用户配置得更好了。

但你大概率还在被几个怪现象困扰：

- **聊着聊着 Claude 突然「变笨」了** —— 前半段回答得有理有据，后半段开始胡言乱语，甚至忘记之前定好的规矩
- **想省钱切个便宜模型，账单反而涨了** —— 对着 Opus 聊了半天，想问个简单问题切 Haiku，结果发现费用比继续用 Opus 还贵
- **装了一堆好用的 MCP Server，可用上下文急剧缩水** —— 本来好好的 200K 窗口，没开始对话就感觉拥挤
- **自动 `/compact` 之后，Claude 把之前定好的架构决策丢了** —— 还得花半小时重新解释

**这些都不是 bug，是你没管好上下文。**

而上下文管理，是 AI 编程从「会用」到「用好」的**分水岭**。这篇我会把这个最底层的心法讲透——从 200K / 1M 上下文的真实构成，到 Prompt Caching 这个 Claude Code 整个架构的核心秘密，再到怎么用 HANDOFF.md 做跨会话的知识传递。

## 一、概念铺陈

### 从 Prompt Engineering 到 Context Engineering

AI 编程这几年的进化可以粗略分成几个阶段：最早是 Tab 补全（GitHub Copilot），然后是 IDE 编辑器里的对话（Cursor、Windsurf），再到现在 CLI Agent 时代（Claude Code）。能力越强，我们用模型的方式也在变——前几年大家还在研究「Prompt Engineering」，也就是怎么把提示词写得更花哨。现在进入了一个新阶段：**Context Engineering**，研究怎么管理 Claude 能看到的全部信息。

这两者的区别是**量级的**。

Prompt 写得花里胡哨，效果提升有限——现在的模型对自然语言的理解已经很好了，你把「请帮我检查一下这段代码」写成「作为一名资深高级工程师，请你以严谨的态度帮我…」并不会让它变聪明多少。

但上下文管理好不好，效果差距可以是「能干」和「完全干不了」的区别。

我见过一句话点破了上下文工程的核心：**很多人把上下文当「容量问题」，但卡住的地方通常不是不够长，而是太吵了，有用的信息被大量无关内容淹没了。**

这句话是整个上下文工程的核心——**问题不在容量，在信噪比**。你塞进去 150K tokens 的内容，Claude 真正需要的可能只有 10K。剩下的 140K 全是噪音，而且这些噪音会挤掉真正重要的信息、干扰模型判断、消耗算力和钱。

### 上下文爆炸的 7 种典型场景

在讲原理之前，先让你对号入座。这是我整理的上下文爆炸的 7 种典型场景，你大概率都遇到过：

**场景 1：一次性读入太多文件。** Claude 为了「搞懂项目」去 grep 整个仓库，一次 cat 了几十个文件进上下文。你还没问问题，上下文已经过半了。

**场景 2：命令输出失控。** `cargo test` 一次完整输出动辄几千行，`npm install` 的 warning、大仓库的 `git log` 都能轻松塞满屏幕。Claude 其实只需要知道「过了还是挂了」，但完整日志已经进上下文了，实打实地消耗 token，挤掉对话历史和文件内容的空间。

**场景 3：反复试错不 compact。** 同一个问题被纠正 2-3 次，历史里全是「刚才那个不对，应该这样」「再改一下」「还是不行」。越到后面，Claude 看到的全是自己之前的错误，越改越偏。

**场景 4：MCP 返回海量数据。** 让 Claude 抓一个长网页、查一个大 JSON、读一个几万行的数据库表，整块塞回来。

**场景 5：Skills 和 MCP 装太多。** 每个启用的 Skill 的描述符都常驻上下文。装 20 个 Skill、接 5 个 MCP，还没开始对话就已经吃掉了近 10% 的上下文。

**场景 6：图片和截图。** 一张截图的上下文成本比几千字纯文本还高，很多人不知道。粘几张界面截图看起来无伤大雅，其实很重。

**场景 7：重复读同一个文件。** Claude 忘了上次读过，又 cat 了一遍。

这 7 种场景有一个共同点：**你在用容量思维，Claude Code 在用噪音思维**。你觉得「200K 那么大，塞点东西没事」，但每次塞进去的都是「噪音」——Claude 不需要但又被迫看的东西。

## 二、核心模型

### 200K 到 1M：上下文窗口的真实构成

先澄清一个最近的重要更新——**200K 已经不是上限了**。

Claude Opus 4.6 和 Sonnet 4.6 现在都支持 **1M（一百万）token 的扩展上下文窗口**。这是一个巨大的升级，但各订阅计划的可用情况不同：

| 计划 | Opus 4.6 + 1M | Sonnet 4.6 + 1M |
|------|---------------|-----------------|
| **Max / Team / Enterprise** | 自动升级，包含在订阅里 | 需要 extra usage |
| **Pro** | 需要 extra usage | 需要 extra usage |
| **API / 按量付费** | 完全访问 | 完全访问 |

Max 用户（包括 Team Standard 和 Team Premium 席位）的 Opus **已经自动升级到 1M**，不需要做任何配置。Sonnet 1M 和 Pro 用户需要开启 extra usage 功能付额外费用。

启用 1M 的方式很简单，用带 `[1m]` 后缀的模型别名：

```bash
# 会话中切换
/model opus[1m]
/model sonnet[1m]

# 启动参数
claude --model opus[1m]
```

或者在 settings.json 里永久设置：

```json
{
  "model": "opus[1m]"
}
```

**定价说明**：1M 上下文使用标准模型定价，**超过 200K 的 token 没有溢价**。Max/Team/Enterprise 订阅包含，Pro 走 extra usage 付费。如果你不想用 1M，可以用 `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` 关掉。

这里有一个很多人会犯的误区：**1M 的到来 ≠ 「不用管上下文了」**。恰恰相反，1M 上下文让你有机会塞更多内容进去，缓存命中率的优化空间更大了——也就是说，Prompt Caching 的重要性**更高**了。这个我们后面会详细讲。

### 可用上下文的真实分层

![200K 上下文真实解剖](https://oss.aiqqyc.com/2026/04/dd06d4b6a7b8bc22b57075ef9c1d4d9a.png)

不管是 200K 还是 1M，都不是全部可用。我之前仔细算过一次 200K 上下文的真实分层，结果让我吃了一惊：

```text
200K 总上下文
├── 固定开销 (~15-20K)
│   ├── 系统指令: ~2K
│   ├── 所有启用的 Skill 描述符: ~1-5K
│   ├── MCP Server 工具定义: ~10-20K  ← 最大隐形杀手
│   └── LSP 状态: ~2-5K
│
├── 半固定 (~5-10K)
│   ├── CLAUDE.md: ~2-5K
│   └── Memory: ~1-2K
│
└── 动态可用 (~160-180K)
    ├── 对话历史
    ├── 文件内容
    └── 工具调用结果
```

把这个结构看三遍，你会意识到一件事：**你以为自己有 200K 可用，实际上能用的只有 160-180K**。

![/context 命令实际输出](https://oss.aiqqyc.com/2026/04/4d7e1795dfdb79be492bdeb00cd5bb39.png)

更扎心的是 MCP 这一块。一个典型的 MCP Server（比如 GitHub）包含 20-30 个工具定义，每个约 200 tokens，合计 4000-6000 tokens。**接 5 个 Server，光工具定义的固定开销就到 25000 tokens（12.5%）**。在要读大量代码的场景，这 12.5% 相当于一大部分对话空间被白白占掉——我第一次算出这个数字的时候，真没想到有这么多。

### 上下文的分层哲学

怎么把有限的空间用好？一个实用的分层原则是这样的：

```text
始终常驻    → CLAUDE.md：项目契约 / 构建命令 / 禁止事项
按路径加载  → rules：语言 / 目录 / 文件类型特定规则
按需加载    → Skills：工作流 / 领域知识
隔离加载    → Subagents：大量探索 / 并行研究
不进上下文  → Hooks：确定性脚本 / 审计 / 阻断
```

核心原则：**偶尔用的东西就不要每次都加载进来**。

这个原则贯穿整个上下文工程。你会发现，我们前面几篇讲的所有能力，其实都在这个分层里找到了自己的位置——CLAUDE.md、Rules、Skills、Sub-agents、Hooks，每一层对应不同的加载策略。

### Prompt Caching：Claude Code 最核心的秘密

![Prompt Caching 工作原理](https://oss.aiqqyc.com/2026/04/08362ed03de57afacc560c25ab6152fe.png)

工程界有句老话：**"Cache Rules Everything Around Me"**——缓存统治了一切。对 Agent 而言，这句话同样成立。

**Claude Code 的整个架构，都是围绕 Prompt 缓存构建的。** 这不是夸张——高缓存命中率不光省钱，速率限制也会松很多。据说 Anthropic 甚至会对缓存命中率跑告警，命中率太低直接宣布 SEV（Severity，科技公司里意味着「P0 级事故」）。他们把 Prompt 缓存命中率看成**产品健康的核心指标之一**。这个信号量足够大了。

那 Prompt Caching 到底是什么？简单说，就是 Claude 的 API 会把你请求里的一部分内容缓存起来，下次请求时如果这部分内容没变，就可以直接复用，**只收 1/10 的价格**。

#### 为缓存设计的 Prompt Layout

Prompt 缓存按**前缀匹配**工作——从请求开头到每个缓存断点之前的内容都会被缓存。

这就是为什么 Claude Code 的 Prompt 是这样组织的：

```text
1. System Prompt     → 静态，锁定
2. Tool Definitions  → 静态，锁定
3. Chat History      → 动态，在后面
4. 当前用户输入      → 最后
```

**静态的内容放前面，动态的内容放后面**。只要前缀（系统 Prompt + 工具定义 + 已发生的对话历史）不变，下一次请求就能命中缓存，享受 1/10 的价格优惠。

#### 破坏缓存的 3 个常见陷阱

理解了前缀匹配的原理，你就知道什么会破坏缓存：

**陷阱 1：在系统 Prompt 里放入带时间戳的内容。** 每次都变，每次都要重建缓存。

**陷阱 2：非确定性地打乱工具定义顺序。** 同样一组工具，顺序不一样就是不同的前缀。

**陷阱 3：会话中途增删工具。** 加一个 MCP Server 或者装一个新 Skill，整个工具定义块都变了，前面的缓存全作废。

那像「当前时间」这种动态信息怎么办？别去动系统 Prompt，**放到下一条消息里传进去就行**。Claude Code 自己也是这么做的——用户消息里加 `<system-reminder>` 标签，系统 Prompt 不动，缓存也就不会被打坏。

这是一个非常聪明的设计：**把动态信息推到后面**，让前面的静态部分始终可以命中缓存。

#### 反直觉：会话中途不要切模型

这条是整个 Prompt Caching 最反直觉的一条，也是很多人不知道就踩坑的地方。

**Prompt 缓存是模型唯一的**——Opus 的缓存 Haiku 用不了，反过来也一样。

想象一个场景：你和 Opus 对话了 100K tokens，现在想问一个简单问题，觉得「用 Haiku 更便宜」，就切过去。结果呢？

**切换到 Haiku 实际上比继续用 Opus 更贵——因为要为 Haiku 重建整个缓存。**

仔细品这句话。Opus 那 100K 的缓存是为 Opus 建的，Haiku 用不了。Haiku 要重新处理整个 100K 的上下文，按 Haiku 的完整定价计费（没有缓存折扣）。即使 Haiku 单价便宜，**重建整个 100K 缓存的成本远远超过继续用 Opus 处理一个简单问题的成本**。

那如果确实需要用便宜的模型呢？**用 Sub-agent 交接**：

- Opus 在主线程里准备一条「交接消息」，说明要完成的任务
- 启动一个 Haiku 的 Sub-agent
- Haiku Sub-agent 在自己全新的上下文里处理这个简单问题
- Sub-agent 干完活返回摘要，主线程继续用 Opus

这样 Opus 的 100K 缓存完好无损，Haiku 在自己的小上下文里工作，各得其所。

**经验法则：一个会话从开始到结束，不要切换模型**。

#### Compaction 的实际实现：开 fork，命中缓存

聊到 Compaction（上下文压缩），很多人以为它是 Claude Code 在本地跑个脚本做摘要。实际上它的实现非常巧妙：

1. **上下文快满时**，Claude Code 检测到
2. **开一个 fork 调用** —— 把完整对话历史喂给模型，加一句「总结这次对话」
3. **命中缓存** —— 因为前缀和主会话一样，这一步只需 **1/10 的价格**
4. **替换历史** —— 原来几十轮对话被替换成 ~20K tokens 的摘要
5. **保留必要信息** —— System + Tools 还在，再挂上之前用到的文件引用
6. **继续新的轮次**

整个 Compaction 过程自己就是 Prompt Caching 的受益者——因为前缀命中，所以摘要成本只有 1/10。如果不走缓存，每次 Compaction 都会很贵，整个机制就不经济了。

#### Plan Mode 的巧妙设计

直觉上，进入 Plan Mode 应该切换到「只读工具集」——把写入工具都禁用。但这样做会破坏缓存，因为工具定义变了。

Claude Code 的实际做法是：**EnterPlanMode 是模型可以自己调用的工具**。检测到复杂问题时，模型自主调用这个工具进入 plan mode，工具集不变，缓存不受影响。

也就是说：**状态在模型侧，工具列表在 API 侧，两者解耦**。这是一个非常优雅的设计——不动缓存前缀的前提下，让模型自己切换行为模式。

#### defer_loading：工具的延迟加载

前面提到 MCP 工具定义是最大的隐形杀手——接 5 个 Server 就能吃掉 12.5% 的上下文。但如果中途移除这些工具呢？**缓存又会被破坏**。

Claude Code 团队怎么解决这个矛盾的？

答案叫 **defer_loading**：

- 请求里只发送工具的**轻量级 stub**——只有工具名，标记 `defer_loading: true`
- 模型通过 **ToolSearch 工具**「发现」这些工具的存在
- 当模型真的想调用某个工具时，**完整的工具 schema 才加载进来**
- 这样缓存前缀保持稳定，上下文占用急剧下降

启用方式：在 settings.json 里加环境变量 `ENABLE_TOOL_SEARCH=true`：

```json
{
  "env": {
    "ENABLE_TOOL_SEARCH": "true"
  }
}
```

效果有多好？根据公开的测试数据：

- **上下文保留率可达 95%**
- **Opus 4 上工具调用准确率从 49% 提升到 74%**

一个配置项带来这么大的提升，装了 MCP 的你必设。

> **进阶了解：Programmatic Tool Calling。** 还有一个更极端的优化方向——让模型用代码编排多个工具调用，中间结果在执行环境中流转而不进入上下文，token 消耗可从约 150000 降到约 2000（75 倍节省）。这个能力目前主要在 Anthropic SDK 层暴露，Claude Code 默认没开启，但思路值得记住：**需要大量中间结果的任务，把数据流控制在沙箱里，只把最终结果给模型**。

#### Prompt Caching 的配置开关

最后一个技术细节——怎么关掉 Prompt Caching：

| 变量 | 作用 |
|------|------|
| `DISABLE_PROMPT_CACHING=1` | 全局禁用，优先级最高 |
| `DISABLE_PROMPT_CACHING_OPUS=1` | 仅禁用 Opus |
| `DISABLE_PROMPT_CACHING_SONNET=1` | 仅禁用 Sonnet |
| `DISABLE_PROMPT_CACHING_HAIKU=1` | 仅禁用 Haiku |

**一般不建议关闭**。只有在调试特定缓存问题、或者某些云服务商的缓存实现有问题时才用。关掉之后你的费用会直接涨 10 倍。

### Agent = Model + Harness

讲完 Prompt Caching，我们往上抽象一层。Prompt Caching 只是 Agent Harness 的一个局部优化。**Agent Harness** 是一套完整的哲学：

> **Agent 能力的提升不再靠训练更强的模型，而是靠设计更好的外部系统（Harness）**。

Harness 包括：

- **文件系统**：作为外部记忆，让模型不用把所有东西都记在上下文里
- **沙箱**：隔离执行环境，防止模型越权
- **上下文压缩机制**：让长对话不至于被撑爆
- **工具链**：给模型调用外部能力的接口

理解 Harness 的意义在于：你不再是「在调教一个模型」，而是「在设计一个系统」。你开始思考哪些东西放在模型的上下文里、哪些东西放在文件系统里、哪些东西通过工具调用、哪些东西由 Hook 自动处理。

**别把确定性逻辑塞进上下文**——这是我最近实践得最受用的一条原则：

> **凡是可以通过 Hooks、代码规则或工具约束表达的内容，都应交给外部系统处理，而不是让模型反复读取。**

举几个实际例子：

- ❌ 每次对话都提醒「别忘了跑测试」 → ✅ 用 PreToolUse Hook 拦截 `git commit`，没过测试直接阻断
- ❌ 让模型每次都检查「这个文件改了没」 → ✅ 用 Hook 自动跑 `git diff`，把结果注入消息
- ❌ 让模型记住「我们用 pnpm 不用 npm」 → ✅ 写到 CLAUDE.md 里
- ❌ 每次编辑完都提醒「记得格式化」 → ✅ 用 PostToolUse Hook 自动跑 prettier

**能用确定性逻辑解决的事，永远不要让模型每次都推理一遍**。

另外，有一个概念叫 **Dynamic Context Discovery**——默认少给，只在需要时读取。文件系统天然适合做这个接口。工具调用经常返回大量 JSON，几次搜索就能堆出成千上万 token。与其让这些数据都塞进模型上下文，不如直接写入文件，让 Agent 通过 `grep`、`rg` 或脚本按需读取。有公开的 A/B 测试数据显示：把工具描述同步到文件夹，Agent 默认只看到工具名，需要时再查询具体定义，**调用 MCP 工具的任务总 token 消耗减少了 46.9%**。

这也是为什么 Claude Code 这么依赖文件系统——它就是模型的「外挂大脑」。

## 三、实践层面

### 上下文管理的 8 个实战策略

#### 策略 1：适时 /compact，但别依赖自动压缩

默认的压缩算法按「可重新读取」判断——早期的 Tool Output 和文件内容会被优先删掉。但顺带**把架构决策和约束理由也一起扔了**。结果就是：两小时后再改，可能根本不记得两小时前定了什么，莫名其妙的 Bug 就是这么来的。

我的经验值：

- **60%** 上下文用量 → 主动 `/compact`
- **80%** → 考虑新开会话
- **别等**到自动压缩触发

#### 策略 2：/clear vs /compact 的选择

很多人把这两个命令搞混：

- **任务切换** → `/clear`（彻底清空，开始新任务）
- **同任务进入新阶段** → `/compact`（保留上下文，压缩历史）
- **同一个问题被纠正 2 次以上** → `/clear` 重来（别让错误污染继续蔓延）

#### 策略 3：Compact Instructions（最关键的一招）

把压缩规则写进 CLAUDE.md，**不让算法猜**：

```markdown
## Compact Instructions

Preserve in priority order:
1. Architecture decisions (NEVER summarize)
2. Modified files and their key changes
3. Current verification status (pass/fail)
4. Open TODOs and rollback notes
5. Tool outputs (can delete, keep pass/fail only)
```

这段话的意思是：「压缩时按这个优先级保留——架构决策永不压缩、已改文件要记住、验证状态要记住、未完成任务要记住、工具输出可以删掉」。

写了 Compact Instructions，算法就知道哪些内容是神圣不可侵犯的。**这是整篇文章最值得你抄走的一段配置**。

#### 策略 4：子任务拆分

一个会话只做一件事。别让它一天跑三个不相干的任务——前两个任务的上下文会污染第三个。

> 🔴 反例：早上让 Claude 改认证模块，中午让它调数据库，下午让它帮你写文档。三个任务的历史互相干扰，效果一定差。

> ✅ 正例：每个任务开始时 `/clear`，任务结束时 `/rename` 存档方便后面 `--resume`。

#### 策略 5：/plan 先规划再执行

Plan Mode 的核心价值不是「生成计划」，而是：

- **探索阶段不动文件** —— 你可以反复和 Claude 讨论方案，不担心它自作主张改代码
- **Claude 可以先澄清目标和边界** —— 在方案确认前不发生执行成本
- **执行成本在计划确认之后才发生**

复杂重构、迁移、跨模块改动**必用 Plan Mode**。这是防止「在错误假设上越跑越偏」最有效的工具。

#### 策略 6：大文件用 @ 引用，不要粘贴

在消息里用 `@path/to/file` 引用文件：

- `@` 引用：只在 Claude 需要时才读取文件内容
- 粘贴文件：整个文件永久进入对话历史，每轮对话都要被处理一遍

养成习惯：想让 Claude 看某个文件时，不要用剪贴板粘贴，直接 `@path` 引用。

#### 策略 7：Tool Output 降噪

命令输出是第二大的隐形上下文杀手。手动控制：

```bash
# 只看前 30 行
cargo test 2>&1 | head -30

# 用 jq 过滤 JSON
curl api.example.com/data | jq '.items[0:5]'

# grep 提取关键信息
npm install 2>&1 | grep -E "(error|warn)" | head -20
```

自动化方案：用 Hook 透明重写命令，对 Claude Code 完全无感。比如 RTK（Rust Token Killer）就是把 `cargo test` 自动替换成精简输出的 Hook。

#### 策略 8：开启 ENABLE_TOOL_SEARCH

前面讲过，这是最立竿见影的优化。装了 MCP 的话必开：

```json
{
  "env": {
    "ENABLE_TOOL_SEARCH": "true"
  }
}
```

几行配置，省几万 tokens 的固定开销。没有理由不开。

### 成本监控与 Fast Mode

#### 成本监控的三个命令

定期跑这三个命令，心里有数：

```bash
/cost    # 当前会话的 token 消耗和费用
/stats   # 订阅的使用模式和历史趋势
/usage   # rate limit 的使用率
```

#### Fast Mode：更快但更贵的 Opus

前面讲了怎么省 token，但有时候你恰恰需要**更快**——代价是更贵。Fast Mode 是 Anthropic 最近推出的加速选项：

- **2.5x 加速 Opus 4.6** 的响应速度
- 定价：30/150 美元 per MTok（比标准 Opus 贵）
- 需要 **extra usage** 功能，不占订阅 rate limit
- 可以和低 effort 组合，速度拉到极致

开启方式：

```bash
/fast on   # 开启
/fast off  # 关闭
```

什么时候用：赶 deadline、做探索性任务、对话密集型工作。日常开发和不急的长任务用标准 Opus 就够了。

### 省钱的 10 个策略

前面散落在各章节的省钱技巧，在这里统一列出来方便你抄：

1. **选对模型** —— Sonnet 够用就不要上 Opus
2. **用 opusplan 混合模式** —— Opus 规划 + Sonnet 执行
3. **及时 /clear** —— 避免历史膨胀
4. **低频指令移到 Skills** —— CLAUDE.md 只保留高频内容
5. **关闭不用的 MCP Server** —— 5 个变 2 个，节省 15K tokens
6. **开启 ENABLE_TOOL_SEARCH** —— 延迟加载工具定义
7. **用 Sub-agent 做探索性任务** —— Haiku 默认，便宜
8. **长任务切 background** —— 不占主线程上下文
9. **大输出命令加 `| head` 截断** —— 降噪
10. **避免破坏 Prompt 缓存** —— 不中途切模型、不动系统 Prompt、不乱动工具顺序

**特别警告**：Agent Teams 的 token 消耗**约为普通会话的 7 倍**，因为多个 Agent 各自维护独立的上下文。用之前想清楚值不值。

## 四、案例：HANDOFF.md 跨会话知识传递

上面的策略都是**会话内**的管理。但有时候你需要跨会话传递知识——比如上下文快满了要开新会话、一个任务分几天做、或者把手头的工作交接给另一个 Claude 实例。这时候 **HANDOFF.md** 是最好的工具。

### 为什么自动 Compaction 不够用

自动 Compaction 的算法有个问题：它可能把架构决策、失败路径、约束理由一起丢掉。我的做法是：在准备切换会话之前，让 Claude 先写一份 HANDOFF.md——写清楚现在的进展、试过什么、什么有效、什么没用。下一个拿到新鲜上下文的 Claude 实例只看这个文件就能继续干活。

**HANDOFF.md 不依赖算法的摘要质量**，而是由你主动写一份结构化文档。这比让算法猜要靠谱得多。

### HANDOFF.md 的模板

```markdown
# HANDOFF.md

## 当前进度
- [x] 完成了用户认证模块
- [x] 数据库迁移脚本
- [ ] 订单状态机（进行中）
- [ ] 支付回调处理（未开始）

## 关键架构决策（不要动）
1. 订单状态用 enum 而不是字符串（性能原因）
2. 支付回调必须幂等，用 idempotency_key 去重
3. 数据库连接池固定 20 个，不要调

## 试过但没用的方案
- 用 Redis 做分布式锁 → 超时问题，改成 PostgreSQL advisory lock
- 把订单状态放 Redis → 一致性问题，放回主库

## 下一步
1. 完成订单状态机的 3 个剩余状态
2. 写状态机的单测
3. 接入支付回调处理

## 验证命令
- 测试：`pnpm test:orders`
- Lint：`pnpm lint`
```

注意这四个板块：**当前进度**、**架构决策**、**试过的方案（含失败）**、**下一步**。第三个板块尤其重要——**失败的方案和成功的方案同样值钱**，它告诉下一个 Claude 实例「这条路别再走了」。

### 实操流程

1. 任务做到一半 → 告诉 Claude：「帮我写一份 HANDOFF.md，我要开新会话」
2. Claude 生成初稿，你**快速扫一遍补缺** → 「再加上我们试过用 Redis 的那个坑」
3. `/clear` 开新会话
4. 新会话：「读 HANDOFF.md，继续上次的工作」

### HANDOFF.md 和 Auto Memory 的区别

这两者经常被混淆：

| | HANDOFF.md | Auto Memory |
|---|---|---|
| **谁写的** | 你主动让 Claude 写 | Claude 自动写 |
| **结构** | 结构化，有明确板块 | 零散，类似日记 |
| **生命周期** | 一次性，任务级 | 持续性，项目级 |
| **目的** | 跨会话交接具体任务 | 跨会话记住项目知识 |

**HANDOFF.md 是短期记忆**，解决「这个任务要分几次做」。**Auto Memory 是长期记忆**，解决「下次做类似任务时别再踩同一个坑」。两者配合使用。

## 小结

![上下文管理 SOP](https://oss.aiqqyc.com/2026/04/9cc2b3d99c8a5dc6757fc9f617bbe4ae.png)

把所有策略串成一个完整的 SOP，你可以抄走当检查清单用。

**任务开始前：**
- 确认 CLAUDE.md 就位且符合项目现状
- 跑 `/context` 检查起始占用（目标：系统 + MCP < 20K）
- 如果占用偏高，关掉不用的 MCP Server
- 明确目标，复杂任务先用 `/plan` 规划

**任务进行中：**
- 关注 Status Line 的上下文百分比
- **60% → 考虑 `/compact`**
- **80% → 主动写 HANDOFF.md → `/clear` 开新会话**
- 遇到大文件/命令输出 → 加过滤器截断
- 同一问题被纠正 2 次以上 → `/clear` 重来
- 想切模型？→ 别切！用 Sub-agent 交接

**任务结束时：**
- `/rename` 给会话起个名（方便 `--resume`）
- 如果学到了新的项目知识 → 让 Claude 自动更新 CLAUDE.md
- 跑一次 `/cost` 看看本次花了多少

---

这篇内容密度很高，因为上下文工程实在绕不开这些细节。如果你只能记住三件事，我希望是这三件：

1. **上下文不是容量问题，是信噪比问题**。塞进去的内容越多，有效信息的密度反而越低。
2. **Claude Code 的整个架构围绕 Prompt Caching 构建**。理解了前缀匹配、defer_loading、Compaction 的 fork 机制，你就理解了为什么「会话中途不要切模型」「不要乱动系统 Prompt」这些建议如此重要。
3. **Agent = Model + Harness**。你不是在调教一个模型，你是在设计一个系统。把能用确定性逻辑处理的事交给外部系统（Hooks、文件系统、代码规则），让模型专注于真正需要推理的事。

特别是 `/context`、`/compact`、Compact Instructions 这几个概念，跑一次和看一次的效果完全不一样。**实操过一遍再回来看第二遍，你会发现很多之前没意识到的细节。**
